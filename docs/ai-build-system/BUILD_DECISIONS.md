# Dealality Build Decisions

This file captures durable product, technical, naming, data, and AI behavior decisions that should guide future builds.

Do not use this as a verbose changelog. Only add decisions that will matter for future work.

## Current Decisions

- Dealality is a hotel deal intelligence platform, not a listing marketplace or generic lead list.
- Dealality should create recurring opportunity intelligence, not one-time lists.
- Airtable is the operational source of truth unless a future migration changes this.
- Memberstack is identity/auth only and should not become the business-data source of truth.
- Do not use Wized. Preferred ecosystem includes Zapier, GitHub, and Railway.
- UI labels should use Proper Case; helper copy should use sentence case.
- Operator Fit Assessment / Operator Match should be called Operator Alignment Snapshot in user-facing product language.
- Brand/operator profile content should not be called validated unless directly validated by the company.
- Use AI-Assisted, Source-Informed, Platform-Derived, Company Published, or Company Validated as appropriate **in Airtable governance fields** (internal classification).
- **Explorer trust-chip external labels are conservative:** they must not imply company approval unless the company directly reviewed or validated the profile. Internal `Validation Status = Company Published` displays externally as **AI-Assisted Profile** with subtitle **Source Basis: Company Materials**. **Confidence Level** / **Data Confidence Level** remain stored for QA/governance but must **not** appear in Explorer trust-chip subtitles (`displaySubtitle`).
- AI outputs should separate evidence, interpretation, and next action where relevant.
- AI should not overwrite company-validated data automatically.
- Future access planning should account for Workspace Access, Region Access, Deal Access, Company Profile linkage, and Demo/Admin behavior.
- Dealality should use options, signals, considerations, questions to clarify, and data gaps rather than overly definitive recommendations.
- Schema authority for Airtable fields lives in `docs/*-airtable-fields.md` and `.env.example` — never invent field names or select options.
- Dealality-defined geography (Market + corridor Submarket) is authoritative for product UI; STR Market/Submarket is legacy reference only.
- Operator Setup legacy writer is primary unless `OPERATOR_SETUP_USE_NEW_BASE_WRITER=1`.
- Scripts with live Airtable writes require `--dry-run` review before `--apply`.
- **Operator Setup - Master** profile governance stores confidence in live column **`Data Confidence Level`** (alias for P1 `Confidence Level`, which is not on that table). Read path and `pilot-profile-governance-values` must map this alias on read/write.
- **Partner Intelligence vs Setup governance:** PI is the **source-level** evidence/review layer (Source Library, Extracted Facts). Brand/Operator Setup **root tables** hold **profile-level** governance fields consumed by API `governance` and Explorer trust chips. **Company Validated** must not be set from Partner Intelligence public-source extraction alone — only from direct company confirmation.
- **PI publish readiness scope (2026-07-06):** Profile-governance publish eligibility is evaluated from **approved Explorer-use sources** and linked **Approved/Edited** facts only. Full linked packages still report excluded/non-approved sources as diagnostics; they do not block publish eligibility. See `lib/partner-intelligence/profile-governance-publish-readiness.js` (`buildPublishScopeSlice`, `assessPackageReadiness`).
- **PI sparse confidence cap (2026-07-06):** Proposed profile-governance **Confidence Level** is capped at **Medium** when publish scope has &lt;3 approved facts and/or identity-only coverage. **High** requires identity + substantive field coverage. `assessPublishScopeConfidence` in the same module; does not change external trust chip mapping.
- **PI source-basis validation (2026-07-06):** `inferValidationStatus` in `profile-governance-publish-readiness.js` classifies approved publish-scope sources by **mapped profile Source Type** (company-controlled vs reviewed/public), not by entity type (brand vs operator). All company-controlled sources → internal **Company Published** → external **AI-Assisted Profile** / Source Basis: **Company Materials**. Mixed or all public/third-party → **Source-Informed** / **Source-Informed Profile** / Source Basis: **Reviewed Sources**. Operator official website captures (`Website Capture` → Company Website) follow the same rule as brand company materials. **Source-Informed** is reserved for third-party, public, mixed, or non-company-controlled packages.
